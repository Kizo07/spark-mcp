## 1. Lifecycle end-to-end — works at service level, unreachable in product

**Verified in code + tests:** draft → challenger → replay → decided → veto → rollback all function against a real DB. `distill_skill` writes `draft` at next version ([skills.py](./src/spark_mcp/skills.py:218)); `propose_skill_challenger` writes `challenger` + pending candidate ([skills.py](./src/spark_mcp/skills.py:439)); `run_replay` persists `eval_scores`/`heldout_gap` onto the pending candidate ([skills.py](./src/spark_mcp/skills.py:675)); `decide_promotion` requires non-null `eval_scores` ([skills.py](./src/spark_mcp/skills.py:885)), flips champion/rollback_target, assigns uniform credit, appends `benchmark_history` ([skills.py](./src/spark_mcp/skills.py:901)); gate path writes the `approvals` row `decided_by='gate'` + notify trajectory event ([skills.py](./src/spark_mcp/skills.py:931)); veto demotes + restores ([skills.py](./src/spark_mcp/skills.py:1103)); `retire_skill` chains `rollback_target` ([skills.py](./src/spark_mcp/skills.py:1176)). Fixture split confirmed: 6 fixtures, 4 held-in / 2 held-out ([replay_fixtures.yaml](./src/spark_mcp/seeds/replay_fixtures.yaml:1)). The Done-when's "champion→challenger→decided" leg is genuinely exercised: in `_two_champion_setup` v3 derives from champion v2 ([test_skills.py](./tests/test_skills.py:539)).

**BLOCKER B1 — `decide_promotion` and `retire_skill` have no MCP or CLI surface.** Grep over `server.py`/`cli.py`/all services: the only callers are tests and `decide_promotion`'s internal `promote_via_gateway` call. MCP exposes `distill_skill`, `propose_skill_challenger`, `run_replay`, `approve` ([server.py](./src/spark_mcp/server.py:483)) — no decide, no retire, no promote. CLI `skills` subgroup is distill/challenger/replay/approve only ([cli.py](./src/spark_mcp/cli.py:120)). An MCP client runs distill → challenger → replay → dead end: `approve(skill)` refuses pending candidates ([skills.py](./src/spark_mcp/skills.py:1090)). Related: nothing ever auto-invokes the gate, so "auto-with-human-notify" is currently "manual-with-optional-notify" — tests pass `decided_by='gate'` by hand. And the gate has no criteria: the verdict is caller-supplied, with no threshold, no challenger-vs-champion comparison (`run_replay` scores only the challenger, [skills.py](./src/spark_mcp/skills.py:643)), so a regressing challenger is promotable. Fix: expose decide/retire (MCP tool and/or CLI), and either wire auto-decide with a documented criterion or downgrade the "auto" claim to operator-decided.

**BLOCKER B2 — veto/ratify can hit the wrong version after a lineage fork (proven live).** `_challenger_for` resolves a candidate to a skills row by `(name, parent_version)` ([skills.py](./src/spark_mcp/skills.py:139)). Interpretation (c)'s fix made this safe for propose/replay/decide, but `approve()` ([skills.py](./src/spark_mcp/skills.py:1095)) and `promote_via_gateway` ([skills.py](./src/spark_mcp/skills.py:732)) share the ambiguous lookup. Repro (in-memory DB, no files): v2 promoted from parent 1 → v2 retired → v3 challenger from parent 1 → v3 promoted → `approve(skill, <cand_v2>, rejected)` returned `applied: {'vetoed_version': 3, 'restored_version': None}`, leaving `{1: 'draft', 2: 'retired', 3: 'rejected'}` — **the veto naming the v2 candidate killed the live v3 champion**. Same fork arises via veto-then-rechallenge (v3 vetoed → v4 from parent 2 shares `parent_version=2` with v3). Fix: store the challenger `skill_id`/version on the candidate row (or candidate_id in challenger lineage) and resolve exactly; add a fork regression test.

## 2. §21 anti-gaming — core discipline holds, gate coverage doesn't

- **Held-out cannot leak into evolution: PASS.** `_op_gepa` filters to held-in before calling the loop ([skills.py](./src/spark_mcp/skills.py:404)); `run_gepa`/`score_population` take only what they're given and GEPA runs with zero LLM calls by design ([evolve/__init__.py](./src/spark_mcp/evolve/__init__.py:15)). `load_fixtures(path)` accepts an override but no service caller passes one.
- **`heldout_gap` honest: PASS.** `abs(mean_in − mean_out)` ([skills.py](./src/spark_mcp/skills.py:662)), in every verdict, persisted on the candidate ([skills.py](./src/spark_mcp/skills.py:677)), alarm threshold in `ResearchConfig` ([config.py](./src/spark_mcp/config.py:225)). Test recomputes it independently ([test_skills.py](./tests/test_skills.py:350)).
- **MAJOR M1 — promotion without full replay evidence.** `decide_promotion` accepts any non-null `eval_scores` ([skills.py](./src/spark_mcp/skills.py:885)). `run_replay(task_ids=[...])` / `suite=...` overwrites the candidate's evidence with a filtered subset ([test_skills.py](./tests/test_skills.py:373) shows filtered runs landing on the pending candidate), so a cherry-picked single-task replay — even held-out-only (`suite="econometrics"` → `n_held_in=0`) — satisfies the gate. Coverage is auditable (task ids are the `eval_scores` keys) but unenforced. Fix: require full-suite coverage for promotion (reject filtered `eval_scores`, or persist `n_held_in/n_held_out`/task list on the candidate and check it in `decide_promotion`).
